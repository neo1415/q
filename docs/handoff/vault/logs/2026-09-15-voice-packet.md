**Decisions**
- Voice answers travel the same `say` / Q-run paths as typed ones; no voice tables, no provider memory — reason: one Q, one authority (doc 11 §17.3, doc 12 §36/§89).
- Bindings tie the provider conversation id to the server-resolved actor before the credential is returned — reason: TM-VOICE-01/02, transcript is never authority.
- The presence is the Q mark in a breathing ring, not an orb — reason: doc 18 §33; the ElevenLabs registry is also behind a bot checkpoint here.
- Two Speech Engine resources (female default, male alternative) on one WebSocket route — reason: Speech Engine overrides only allow `firstMessage`, so voice choice cannot be a per-session override.

**Open questions**
- ngrok is now authenticated; the tunnel hostname changes on every restart, so `pnpm voice:setup -- --ws-url …` must be rerun each time (a reserved domain would end this).
- Pending confirmations in the interviewer are process-local, like bindings.
- The typed (chat) interview path in the web still uses the scripted `say` flow; only voice goes through the interviewer.
- Root cause of "I'm having trouble thinking": Groq free tier is 8k tokens/minute per model and a turn was 4.9k tokens; the only fallback was a Google model with no key. Both GROQ keys may share one organisation's quota (limits are per org).
- Speech Engine protocol carries only final user transcripts: Q cannot backchannel ("mm-hm") while the person is still speaking. That needs the full ElevenLabs agent or a self-hosted pipeline.
- The interview smoke's attribution uses a placeholder tenant, so its ledger writes fail (warn only); resolve the real tenant from the token before relying on its cost rows.
- Multi-instance deployment needs a shared binding store keyed by provider conversation id.
