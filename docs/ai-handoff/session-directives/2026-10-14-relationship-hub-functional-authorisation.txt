## 2. Functional architecture — one hub, two perspectives

Build a single integrated relationship-management capability consumed through two different experiences.

### Investor Investment Hub

Integrate:

- Investment opportunities and existing relationships
- GateQ applications and dossiers
- Discover-sourced opportunities
- Investment pipeline and review status
- Mandate qualification and investment intelligence
- Meetings, transcripts and action items
- Documents, versions and evidence
- Messages and private team notes
- Due diligence and outstanding requests
- Q Work agents, jobs, reports and approvals
- Investment decisions and outcomes
- Portfolio monitoring where existing source data supports it
- Reports, exports and management actions

### Founder Fundraising Hub

Integrate:

- Existing and prospective investor relationships
- Investor mandate and suitability context
- GateQ applications and submission history
- Fundraising rounds, targets and commitments
- Meetings and communications
- Investor requests and diligence obligations
- Shared documents and company updates
- Reminders and follow-up actions
- Founder-private notes
- Q Work activity relevant to the founder
- Fundraising progress and reporting

Keep both views permission-aware and correctly scoped.

No duplicated canonical company, investor organisation or relationship.

A GateQ application is not automatically evidence of investor interest or an authorized canonical relationship. Preserve the existing application-to-relationship rules.

Relationship state must derive from canonical events, not from a new mutable CRM stage field.

Keep Readiness, Quality, Fit, Interest, Relationship State and Outcome distinct.

## 3. Create reusable functional contracts, not design-specific logic

The most important architectural requirement is future redesignability.

Build functionality through existing bounded modules and typed/versioned interfaces.

Provide coherent capabilities for:

- Hub overview reads
- Relationship and opportunity queries
- Saved views and filters
- Sorting and cursor pagination
- Selected-record context
- Activity/event aggregation
- Meeting/transcript access
- Evidence and document access
- Authorized exports
- Action preparation and approvals
- Q contextual navigation
- Q Work references
- Notifications and task summaries

Use existing APIs where possible.

Where a new read model or contract is genuinely needed, define it cleanly with explicit module ownership, authorization, Zod validation, source references and versioning.

Never introduce arbitrary cross-module SQL queries simply because the Hub needs aggregated information.

The frontend should primarily render returned data and invoke typed actions.

Business rules, access checks and canonical state changes belong in the owning backend modules.

### Future redesign requirement

A later engineer should be able to replace the Hub's page layout, tabs, cards, typography and animations without rebuilding:

- Search/filter services
- Saved views
- Export logic
- Relationship operations
- Q controls
- Evidence retrieval
- Transcript handling
- Approval workflows
- Work/job integration

Do not embed critical business decisions inside React rendering components.

Build functional production screens using Capital Q's actual:

### Copy and hierarchy

Avoid verbose descriptions, excessive explanatory paragraphs, decorative labels and repeated instructions.

Prioritize:

1. What matters?
2. Why does it matter?
3. What is the next available action?
4. Where can the user inspect details?

Use concise labels and progressively disclose secondary information.

Show important facts upfront; make supporting evidence one or two intuitive interactions away.

Users must still be able to find advanced functionality without asking Q.

### States and transitions

Although the full motion redesign is deferred, define and correctly implement semantic UI states now:

- Initial loading
- Skeleton/streaming
- Ready
- Empty
- No search results
- Partial data availability
- Stale data
- Unauthorized
- Action pending
- Awaiting human approval
- Completed
- Failed
- Retry/recovery
- Background Q Work running
- Background Q Work blocked
- Document uploading
- Document processing
- Evidence ready/blocked
- Export preparing/ready/expired

Transitions between these states must be deterministic and accessible.

Use existing lightweight animation and motion conventions where appropriate. Respect reduced-motion preferences.

Do not add elaborate visual animations or cinematic decoration.

Keep functional transitions, focus management, loading feedback and state ownership independent of their eventual animation design.

## 5. Conventional CRM functionality must actually work

Implement real capabilities rather than decorative buttons.

### Search and filtering

Support appropriate combinations of:

- Company/investor
- Sector
- Geography
- Stage
- Relationship state
- Owner/assigned team member
- Opportunity source
- Investor qualification
- Outstanding evidence
- Pending decisions
- Upcoming meetings
- Follow-up dates
- Last interaction
- Work status

Use server-authorized filtering and sorting where needed for correctness and scale.

### Views

Provide usable:

- Table view
- Board view
- Relevant timeline/activity view
- Detail view

These must be different presentations of the same canonical records.

Board movement must not silently change relationship state. Any real transition must go through the existing authorized action/event workflow.

Implement saved views, configurable visible columns and persistent user preferences using established patterns.

### Records and history

A company/investor relationship record should aggregate permitted:

- Summary
- Current status
- Relevant assessments
- Latest actions
- GateQ results
- Meetings and transcripts
- Messages
- Documents and evidence
- Diligence
- Q Work
- Decisions and outcomes
- Historical events

Use existing record URLs and relationship identity.

### Exports and reporting

Make filtering, downloads and exports functional.

Reuse current PDF/CSV exports and existing report services.

Add XLSX or other structured export only where justified, with correct types and safe encoding.

Exports must reflect the selected authorized scope and filters, not silently export every underlying record.

Protect private notes, undisclosed documents and role-specific information.

Support export progress, failure/retry handling, expiry and audit logging as appropriate.

Do not mark an unavailable export format as functional.

### Collaboration

Reuse existing assignments, notes, reminders, messaging, meeting proposals, diligence requests and human approval mechanisms.

Add missing integrations only when necessary.

Do not recreate them as separate CRM subsystems.

## 6. Q must fully operate the Hub

This is an essential product capability, not a future decorative enhancement.

Use existing Q navigation, action, page manifest, semantic control and receipt infrastructure.

Inspect and extend:

- `fast-navigation.ts`
- `app-routes.ts`
- `q-control-runtime.tsx`
- `registry.ts`
- `perform.ts`
- `manifest.ts`
- Existing Q action, retrieval, permission and navigation lifecycle contracts

Q must genuinely be able to:

- Open the Hub
- Switch role-appropriate areas
- Select tabs
- Search and apply filters
- Change saved views
- Open a record
- Expand sections
- Scroll to a precise section
- Open authorized documents
- Navigate to an evidence page or passage
- Open meeting transcripts
- Jump to transcript timestamps
- Display authorized GateQ results
- Navigate into Q Work
- Open an agent report or approval
- Return to prior context
- Recover after interrupted navigation

Use stable semantic identities and actual page actions.

Do not build a separate navigation engine for the CRM.

Do not let the model invent DOM selectors or claim actions completed before receiving valid completion receipts.

### Q must understand the current context

The Hub should provide Q with structured, permission-filtered context for:

- Current organization
- Active role
- Selected relationship/company/investor
- Active tab/view
- Relevant filters
- Authorized evidence references
- Recent relationship events
- Pending actions
- Current Q Work jobs

Make it possible to ask:

"Q, what's important today?"

"What changed with this company since its GateQ application?"

"Show me the last meeting and the outstanding action items."

"Open the financial statement supporting that claim."

"Which founders have not responded to our diligence requests?"

"What have my agents completed on this opportunity?"

"Compare these companies by mandate fit, evidence and unresolved risks."

Q's answers must come from actual authorized structured data and source-aware retrieval, not fabricated summaries.

### Q speed

Routine navigation, tabs, filters and scroll operations should not wait for a full LLM response.

Reuse fast deterministic controls and prefetching where applicable.

Build a scoped, efficiently refreshed briefing read model so Q can immediately access important current information, then investigate deeper when required.

Q's memory remains contextual, permission-sensitive and derived. It is not the canonical CRM source of truth.

Do not regress fast Q navigation, voice control or other existing functionality.

Benchmark relevant operations against the current Q navigation baseline and report measured results.

## 7. Q Work and agent activity

Q Work must appear as part of the relevant relationship and Hub experience.

Reuse the existing persisted workforce/work runtime, not a new agent system.

Show authorized:

- Active jobs
- Progress
- Assigned agent
- Completed work
- Source-linked reports
- Generated artifacts
- Failures
- Retry/recovery
- Pending approvals
- Consequential actions awaiting human authorization

Every item should link to its real existing work record.

Q must be able to open these items and use permitted outputs in its analysis.

Do not simulate completed jobs in production.

Do not automatically execute actions merely because an agent recommended them.
