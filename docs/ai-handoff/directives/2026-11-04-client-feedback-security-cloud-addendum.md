## D. Cloud engineering and continuous deployment: use what exists

The Capital Q repository already contains:

- `.github/workflows/ci.yml`: push/PR checks with Node/pnpm, static checks, tests, build, Postgres/pgTAP; read-only workflow.
- `docs/ai-handoff/START-HERE.md`, `STATE.md`, `HANDOFF-LOG.md`: source of truth for branch ownership, deploy SHAs and release gates. The repo's longstanding deploy path is **integration branch -> CI branch `recovery/2026-09-12-8y2j4w` -> gated deployment branch `recovery/2026-09-12`**. Confirm against latest state and Railway configuration before use.
- `scripts/preview.mjs`: independent local preview with separate worktree, build and DB. This **does not automatically provide a cloud staging instance**.
- Railway application services `web`, `api`, `q-api`, `workers`. These serve the application; they are **not a hosting substitute for Claude's coding sessions**.

### Recommended cloud operating model

1. **Cloud coding agent:** Use Claude Code cloud sessions at https://claude.ai/code (or `claude --cloud` where supported) connected to `neo1415/q`, each in an isolated branch/PR. It can continue a bounded task after the laptop closes. Do **not** assume one task is literally a perpetual 24/7 agent; once completed, that cloud session stops until new work is dispatched. Check subscription, quota and usage costs before initiating parallel tasks.
2. **Cloud CI:** Keep GitHub Actions responsible for checks. Add needed regression suites/coverage on a reviewed branch rather than creating a shadow CI pipeline. CI failures block merge/deploy.
3. **Cloud staging:** Deploy to a separate Railway **staging** environment/URLs with a separate Supabase staging database, auth credentials and storage; use fictional sanitized seed companies and properly licensed videos. Do not point staging at production Supabase or copy real private data. Existing local preview can remain for fast browser checks.
4. **Automatic staging release:** After merged/approved staging branch passes CI, let Railway's GitHub autodeploy trigger **staging**. Require real smoke checks for typed Q, realtime voice, artifact opens, permissions, approvals, and Q Pitch video.
5. **Controlled production release:** Use the repo's existing production branch and Railway auto-deploy only after owner approval, green security/tenant/e2e gates and a known rollback SHA. No autonomous migrations, RLS weakening, production data deletion, mass messages, provider purchases or uncontrolled deploy loops.
6. **Longer-running automation:** Use explicit event-triggered or scheduled GitHub workflows/tasks for narrowly scoped issue triage, tests, or reports. Bounded triggers, costs, concurrency, retries, auditing and repository rules are mandatory. A continuously running Railway AI engineer is unnecessary and an unmanaged cost/security hazard.

### Token and secret policy

- **Do not paste Railway or Supabase API tokens into this chat, a Claude prompt, a GitHub issue/PR, or a committed `.env`.** Never put a PAT in a screenshot. Do not supply service-role/admin production DB credentials merely to make tests convenient.
- The handoff's `ACTIVE-TASKS.md` already includes **"Rotate tokens pasted in chat (Railway, Supabase)"** as an open owner task. Treat previously exposed tokens as needing prompt review and rotation before adding cloud autonomy.
- Start by using the existing Railway GitHub integration, so **a fresh Railway personal access token may not be needed at all** for autodeploy. For Supabase schema work, use migrations through the approved CI/release lane; a separate credential is needed only if an approved tool explicitly requires it.
- If an external provider/API/secret is genuinely required, the agent must name provider, exact scope, environment, expected usage/cost, creation and revoke steps, and **pause until the owner provisions a least-privilege credential through the provider's secure secrets UI**. Keep production tokens separate from staging tokens. Never output secret values or logs containing them.
- For initial cloud setup the owner should connect GitHub to Claude Code in its own UI, authorize the right repo, then set cloud environment/install commands using Node 24 and pinned pnpm. Validate checkout and `pnpm install --frozen-lockfile` before provider credentials.
