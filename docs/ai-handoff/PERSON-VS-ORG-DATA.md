# Person-owned versus organisation-private data on revocation

**Status: ANALYSIS, PROPOSED** (security lane, 2026-11-12). No policy, migration or code was changed. Rows marked **OWNER** need a product-owner decision.

## The rule we must meet (locked sources)

- **PADL #145 (LOCKED), "Separate Persistent Person Identity From Organisation Context":** "Information remains attached to the entity and context to which it belongs rather than automatically following an individual between organisations." "Personal Q continuity can follow the individual. Organisation-owned intelligence remains with the organisation. Role/membership determines organisational access and authority." "Leaving an organisation removes future access without erasing historical participation." "Organisation-confidential intelligence does not follow employees to future employers." "Personal-private activity does not automatically become organisational memory."
- **PADL #151 (LOCKED):** "Organisational information remains organisational when individual members leave." "Appropriate user-owned information should be exportable."
- **Product Specification §8.5.4:** "Organisation-owned information remains under organisational control after an individual employee leaves. The uploader does not automatically own organisational information."
- **Final System Review §21:** "Person ≠ Organisation ≠ Membership/Role."

So the test for each table is: whose facts are these? Facts about the person, written by the person, survive revocation and stay visible to them. Facts about the organisation or its company, even if typed by that person, end with the membership.

## How the server enforces it today

Server SQL runs as `postgres` (bypasses RLS, ADR 0065). The actor-context resolver refuses a revoked membership (`membership_status = 'active'` in `actor-context-resolver.ts`), so a revoked member gets no organisation context on the next request. Capability checks also re-read the membership (`authorization-policy-source.ts`). Use cases that check only `user_id` (and sometimes `tenant_id`) do not re-check the membership, so for them a personal (context-free) sign-in or a stale context still reaches the rows. The new `*.tenant-isolation.integration.test.ts` suites record this.

## Decisions requested

1. Onboarding: end access to company-bound sessions on revocation (recommended).
2. Q conversations opened in an organisation context: end on revocation, and offer an export of the person's own turns.
3. `founder_background_entries.supporting_document_id`: confirm the handling after the founder leaves the company.
4. Confirm that `founder_person_facts` and `founder_profiles` are person-owned and survive revocation (recommended: yes).
