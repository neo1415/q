# Scale ceilings and how to raise them (18 Nov 2026)

Decision 104 asks the lead to report the real ceilings for a scale target of "towards a million users", not to test 10–20 people. This audit was read-only: no load test, no paid call, no write and no variable change.

**How sure each number is:**

- **[P]** read from production on 18 Nov: Postgres settings and catalogues, `ai_ops.model_usage`, `q_runtime.runs`, and the Railway service manifests, metrics and variable names.
- **[C]** read from code or config on `origin/fix/resume-asking-cv9ru3` at `4f26efced`.
- **[D]** from the provider's public price or limit pages as known to the lead. Verify each in the provider's dashboard before relying on it.
- **[E]** an estimate. The working is shown.

## 1. Where production stands today

- **Every service is one replica** [P]: web, api, q-api, workers and clamav, all in europe-west4.
  - Each replica's limit is 8 vCPU and 8 GB. That is the Hobby plan's per-service ceiling, so confirm the Railway plan.
  - The busiest hour in 7 days used at most 0.04 vCPU. Peak memory was 1.85 GB for q-api, 1.59 GB for workers, 1.29 GB for api, 0.94 GB for web and 1.10 GB for clamav.
  - So compute is nearly idle. Node runs the JavaScript on one core per process, so seven of each replica's eight vCPUs can never be used.
- **Database** [P]: PostgreSQL 17.6 on Supabase Pro (the owner upgraded on 25 Oct after the egress-quota restriction).
  - `max_connections` is 60, `shared_buffers` 224 MB and `effective_cache_size` 384 MB, which matches the smallest paid compute size (Micro, 1 GB).
  - The database is 620 MB. Storage holds 4,780 objects (226 MB).
  - It runs in eu-central-1, while Railway runs in europe-west4, so every query crosses providers.
  - There are 1,449 auth users.
- **Connections** [P]: 18 Supavisor server connections and about 13 others (platform, storage, cron, exporter).
  - api and workers use the session pooler with `DATABASE_POOL_MAX=3`.
  - q-api uses the transaction pooler with pool 10 and its connection gate (runbook `transaction-pooler-retry.md`). Each process also holds one session-mode LISTEN connection.
  - The runbook records a Supavisor pool of 15 server connections on this tier, shared by every service.
- **Q load** [P], over the last 14 days:
  - 915 runs, averaging 5.4 model calls, 82k tokens (p95 206k) and $0.022 (p95 $0.076) each.
  - The busiest minute ever had 34 runs.
  - Model calls peaked at 75 per minute and 842k tokens per minute on the main provider, with no rate-limit refusals.
  - 35% of input tokens were cache hits.
  - The busiest spend day was $10.27 (12 people). In the last 30 days 60% of model spend happened outside runs: realtime voice $30, background work $11, delegated work $4. Total spend was $78.59 across 248 people.
- **Run time** [P]: ANSWER p50 10.2 s and p95 49.6 s. MULTI_SOURCE p50 15.3 s. CONTEXTUAL_FOLLOW_UP p50 9.3 s.
- **Model call failures** [P]:
  - FAST_CLASSIFICATION fails 24.6% of the time, mostly `CANCELLED` speculative calls, and costs more than NORMAL_DIALOGUE ($15.23 against $8.71 over 14 days).
  - OpenAI also recorded 367 `TIMEOUT`s.

## 3. Plan by step, with rough monthly cost

**Rule of thumb [E]:**

- One million registered users is typically about 100k daily users and about 10k concurrent at peak.
- Assume an active person asks Q about once every three minutes, and a daily user makes about 5 runs a day.
- **Model spend dominates every band.** At today's $0.022 a run and today's mix it is about **$3.30 per daily user per month**, before voice. The bands therefore give two figures:
  - "now": cost per run unchanged;
  - "target": cost per run cut to about $0.008 through fewer tokens, more caching and cheaper classifiers.

| -------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------- | -------------------------------------------------------- |

**For the owner:** the infrastructure to reach about 1M registered users (10k concurrent) costs tens of thousands a month. The model and voice bill is ten times that unless the cost per run falls. The single most valuable engineering lever is cutting tokens and cancelled calls per run.

## 4. Proposed load test (owner approval needed; do not run now)

- **Target:** staging only (decision 104: the current project becomes staging).
  - Use synthetic `*@fictional.capitalq.local` accounts and production-shaped settings: same compute, pooler modes and replicas.
  - Model and voice providers point at a **mock gateway** for steps 1–3. Only step 4 makes a small, capped number of real calls.
- **Steps** (each held for 10 minutes, with a ramp, a soak and a ramp-down):

  | Step | Synthetic users | What runs                                           | Real model calls |
  | ---- | --------------- | --------------------------------------------------- | ---------------- |
  | 1    | 100             | Mock models                                         | None             |
  | 2    | 300             | Mock models                                         | None             |
  | 3    | 1,000           | Mock models; adds the stream, chat and Discover mix | None             |
  | 4    | 100             | Real models, run budget $25                         | Yes, capped      |

- **What to measure:**
  - p50, p95 and p99 for sign-in, Discover, POST /runs (time to first event and to completion), SSE delivery delay, chat, and document upload to parsed;
  - error rates and 429s;
  - Postgres CPU, memory, active and waiting connections, Supavisor client queue, `idle in transaction`, 57014 count, lock waits and slow statements (`pg_stat_statements`);
  - Railway CPU and memory per replica, and event-loop delay;
  - outbox and pgmq lag, and documents per minute;
  - egress per user;
  - stuck runs, using the runbook's stalled-run query.
- **Pass bar:**
  - steps 1–3 hold p95 POST /runs first event under 3 s;
  - no stuck run;
  - no pool wedge;
  - error rate under 0.5%.
- **Cost estimate** [E]:
  - Railway replicas and a larger staging compute for one day: about $30–80.
  - A load generator (k6 or Artillery on a small VM): about $5–20.
  - Step 4's real model calls: ≤$25.
  - **Total about $60–125.**
