## Method

- **Data:** read-only SQL through `scripts/handoff/live/hosted-read.mjs` against these tables:
  - `q_runtime.runs`, `run_events`, `conversation_messages`, `conversations`, `voice_line_turns`, `conversation_tool_results`, `actions` and `approvals`;
  - `ai_ops.model_usage`.
- **Logs:** q-api Railway logs for 15 Nov 16:00–17:24, fetched in 3-minute windows so the 5,000-line cap never truncated. Earlier deployments are no longer listed by Railway, so **their logs are not retrievable**.
- **No model calls, browser or messages.**
- **Deployed SHA:**
  - Railway keeps only the current deployment (`84ac9afa7`, 15 Nov 14:36) plus failed builds.
  - From 5 Nov 21:26, the q-api SHA per session is therefore the last push to `recovery/2026-09-12` (local reflog) plus 8 minutes for the build.
  - Before that, it comes from the HANDOFF-LOG deploy entries.
  - Every SHA is **approximate**. Rows with `?` had no recorded deploy hour.
- **Sessions:**
  - A _voice_ session is one `voice_session_id`.
  - A _text_ session is the typed runs of one conversation with no gap over 30 minutes.
  - Two typed runs inside voice windows (`ca750f19` on 5 Nov, `d135fa67` on 10 Nov) are counted as text.
- **Turns:**
  - A voice utterance is consecutive transcript segments of one side within 2.5 s, or a continuation that starts with punctuation within 10 s.
  - Each Q run is one Q reply. Its spoken relay is folded into `spoken`.
  - Each voice line not relaying a run is its own record: opening, holding, voice-only, navigation receipt or work notice.
  - Each approval decision is a user turn, and so is each card-driven `PREPARE_ACTION` run.
