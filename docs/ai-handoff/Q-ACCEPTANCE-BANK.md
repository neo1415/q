# Q acceptance bank — what founders and investors ask, and what must happen

Owner direction (2026-10-28): keep thinking of what founders and investors
will want from the Q page; the UI must show the right artifact, Q must do the
right thing, know when to search the web and when not to, and be fast. No
silly mistakes. This bank is the shared list. Every row is run live (typed;
voice where a device allows) before a release is called good, and a row that
fails is a defect to fix, never a row to delete.

Columns: **Ask** (as a person would type or say it) · **Expected artifact**
on the Q page (card/block kind, or "text") · **Action** (what Q may do and
through which gate) · **Web?** (never / only if not on Capital Q / yes) ·
**Budget** (time to the first useful words, p50).

Rules that apply to every row:

- Q answers from Capital Q's own record first. The open web is searched only
  when the subject is not on Capital Q, or the person asks for public
  information, or the task is research by nature. Never for "what did X
  say", "who is interested", "what's my…".
- Anything consequential (message, interest, profile or mandate change,
  booking) is prepared and shown on the approval card; "yes" / "approve" /
  "send it", typed or spoken, approves the one card waiting. Nothing is
  sent or changed without it.
- Unknown stays unknown: no invented numbers, no "poor company" from missing
  evidence. Private material never crosses sides (founder-private to an
  investor, investor-private mandate to a founder).
- Speed: a question answered from the record ≤ 4 s to first words; a card
  answer ≤ 6 s; a web-research answer says what it is doing within 2 s and
  finishes ≤ 25 s. Swipe, Save and Pass never wait on Q.
- Same conversation continues after Q opens another page and the person
  comes back.

## How a run is scored

A row passes only when the artifact is visible on the Q page (screenshot and
DOM text), the action went through the right gate, no web call happened
where "never" is marked (check `ai_ops.model_usage` purpose RESEARCH and the
research ledger), and the time is within budget at p50. Each run records:
account, width, view (chat / presence), timings, model spend, and the
screenshot per row. Failures go to `ACTIVE-TASKS.md` as defects.
