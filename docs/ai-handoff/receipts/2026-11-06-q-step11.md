## A. Speed

### A1. Conversation state cached per conversation, and its save taken off the reader's path

- **`q-runtime/src/application/conversation-state-cache.ts` (new):** an in-process cache of the last **committed** state and summary revision.
  - **Key:** tenant + owner + conversation. An entry is filed under its own state's identity, so one person's state is never served to another (tested).
  - **Bounded:** 1,000 entries, LRU; entries age out after 10 minutes.
  - **Monotonic:** a state never moves back a version, and a summary is never replaced by an older revision.
  - **Wiring:** hung on the Postgres state repository (`cache`), so the answer path and the memory learner share one cache per process.
- **`q-specialists/src/answer.ts` `loadConversationState`:**
  - **A follow-up that continues this process's fold reads nothing from the store** (`continuesFrom`): the cached state's newest message is in the history, and at most one of the person's messages (this turn's) follows it.
  - Anything else reads the store, as before. That covers a turn served by another instance (whose learner may have appended a summary here unseen), or a turn this process answered without folding.
  - **The save is no longer on the reader's path.** It used to be BEGIN/UPDATE/COMMIT before the reader could start. The fold returns at once, and the save runs beside the turn as one short transaction (no model call inside it).
  - The cache is updated only after the save commits. A refused save (another writer won) or a failed save forgets the entry.
  - The run's `answer` resolves only once the save has settled, so a run never ends with its write in flight.
- **Memory learner:** after a summary revision commits, it calls `noteSummary` on the same cache, so the next turn served from the cache sees it.
- **Round trips before the reader, per follow-up turn:**
  - before: 2 parallel reads, then a 3-statement save transaction;
  - after: **0** on a cache hit, 1 parallel read on a miss.

### A2. Reader, retrieval and memory recall in parallel; the bound part refined after the reading

The warm prepare already ran beside the turn reader, covering context assembly (document retrieval), memory recall and the profile. Measuring showed a real defect on that path:

- **The warmed prepare searched before the reading existed.** So step 5's ledger focus (`retrievalFocus`) and the compound `askParts` never reached document retrieval on the warmed path, which is the main path. Only a cold prepare used them.
- **Fix in the gateway `answer`:**
  - When the prepare was warmed and the reading brings a focus or two or more parts, `context.assemble` is asked again with the turn's own request.
  - It starts right after the prepare and is awaited only when the prompt is assembled, so it overlaps the early lead, readiness and the other reads.
  - If the refinement fails, the warmed result is kept.
- **Fix in `q-knowledge` `evidence-retrieval.ts`:**
  - The port keeps one assembled result per run, plan id, latest message and query plan (64 runs, LRU).
  - A reading that changes nothing about the searches is the first search's result, with no second search.
  - Nothing is shared across runs, plans or people. A failed search is not kept.
- **Unchanged:** memory recall (step 9's lane) and authorisation. The refine uses the same plan, envelope and firewall.

### A3. Summary compaction off the critical path

This was already the case, verified rather than changed:

- The running summary is written by the memory learner (`apps/q-api/src/composition/memory-learner.ts`).
- It runs detached after the run's handle resolves (`withLearning`), so it never delays a reply.
- It goes through the Model Gateway by task class `STRUCTURED_EXTRACTION`.
  - That class is routed to the BASIC-tier policy (`structured_extraction.v1`: gpt-5.6-luna, then flash-lite / flash), the same small model as dialogue.
  - The flash-lite-first class is `FAST_CLASSIFICATION`. Moving the memory extraction call to it would also change memory-item extraction quality, so it is not done here; that is an owner or lead routing decision.
- The only change is the cache note above.

### A4. Deterministic per-stage timing (q-api logs)

- **`model-gateway/src/q/stage-clock.ts` (new):** sums a stage's time and counts its runs. The clock is injected, so tests read exact figures. It records names, milliseconds and counts only, never words.
- **New fields on the "q answer produced" log line:**
  - `checks`: `{claimCheck, promiseCheck}` per streamed sentence, and `{claimCheckAnswer, promiseCheckAnswer}` on the stored answer, each `{ms, runs}`;
  - `firstTextMs`: the model's first words, from the seam's start;
  - **`firstSentenceSinceMessageMs`: the first sentence the person got, counted from their message (the p50/p95 bar's figure);**
  - `retrievalRefineMs`: the reading-bound search.
- **New fields on "q turn timing":** `stateMs` and `stateCached`. There is also a debug line, "q conversation state read".
- **Existing fields:** `readMs` (reader), `prepareMs.*` (assemble = retrieval, memory, profile and every pre-read), `phases.*` and `totalSinceRunMs`.
- **Reading production per stage:** filter q-api logs on these two messages. Reader = `readMs`; retrieval = `prepareMs.assemble` + `retrievalRefineMs`; pre-read = `prepareMs.reads` / `prepareMs.wide`; first token = `firstTextMs`; checks = `checks.*`; bar = `firstSentenceSinceMessageMs`.
- **`q-evals/src/dev/q-speed.ts` (new):** runs Q-IQ cases through the real runtime with the scripted model and prints p50/p95 per stage from those log lines.

  ```
  DATABASE_URL=postgresql://postgres@127.0.0.1:54329/cq node packages/q-evals/dist/dev/q-speed.js [--limit N] [--out f.json]
  ```

How to read these:

- **Loopback is sub-millisecond.** A database round trip here is far below a millisecond, so the round trips removed (up to 2 reads and 3 save statements per follow-up) barely show.

- **The largest deterministic stage is the step 6 claim check:** about 4.5 ms per sentence and per answer. It is small, but it is the first thing to look at if the checks show up on production.
- **The bar (p50 ≤ 2.5 s, p95 ≤ 6 s to first sentence) is a production measurement.** Read `firstSentenceSinceMessageMs` once this is deployed.

## Limits and next steps

- **Production latency is not measured here** (no deploy). After deploy, read `firstSentenceSinceMessageMs` p50/p95 and `stateCached` from q-api logs; the bar is ≤ 2.5 s / ≤ 6 s.
- **The cache is per process.** With several q-api replicas, a turn on another instance reads the store, which is no worse than before.
- **The refine adds one search** only when the reading's focus or parts change the query plan. That is a correctness fix (step 5 on the warm path), measured by `retrievalRefineMs`.
- **Summary compaction model:** to move it to the flash-lite-first class, split the summary from memory-item extraction, or re-route `structured_extraction.v1`. That is a lead decision.
- **The integration job is not in `quality`'s `needs`.** The integration owner decides whether it gates deploys.
