## What was built

All of it is deterministic code. Nothing new calls a model on the retrieval path.

- **Query rewriting from the ledger** (`packages/q-knowledge/src/retrieval/query-plan.ts`). It finds the turn's entities in priority order:
  1. **BOUND**: the refs the step-3 reader bound, checked against the shown ledger.
  2. **NAMED**: ledger names that appear in their words.
  3. **RECENT**: used only when there are none of the above.

  For example, "and its burn?" with E1 Silo Credit bound becomes `Silo Credit and its burn?`, filtered to Silo Credit's id. A person or a deck is filed under the company it belongs to (`of`). Only a record uuid is ever used as a filter. A RECENT guess can add a filtered search, but the unfiltered words are always searched too, and the guess never steers the reranker.

- **Multi-query.** The planner makes:
  - one search per subject;
  - one search per part of a compound ask, split by punctuation only (sentence, `?`, `;`, line break), never by keywords;
  - searches from their previous messages (up to three, newest first) under this turn's subjects, weighted 0.5, 0.25 and 0.125. This handles "same question for Silo Health", "I meant Ledgerfold" and "and the other one?" after a clarify.

  The cap is four searches. They are fused by N-way RRF (`fuseRankedLists`). The fused candidate cap scales with the number of searches, so a second company in a comparison isn't crowded out.

- **Reranker behind a port** (`retrieval/reranker.ts`). `reranker` is now `"NONE" | "LOCAL_FIELD_OVERLAP_V1"`. The local reranker adds up:
  - idf-weighted term overlap over the candidates;
  - an entity match (the subject is filed under, or the chunk names, a focus entity);
  - a document match;
  - a small fused-rank prior;
  - a same-subject diversity penalty when two or more entities are in focus.

  Its weights are versioned in `LOCAL_RERANKER_WEIGHTS`. A model reranker can be added later through the Model Gateway behind the same `RetrievalReranker` port. No provider SDK is involved.

- **Config.** `DEFAULT_RETRIEVAL_CONFIG` is now `capital-q-hybrid-v2`: v1's candidate counts, plus `maxSubQueries: 4` and the local reranker. `RETRIEVAL_CONFIG_V1` keeps the old baseline: one search, fused order.
- **Wiring.** `QAnswerRequest.retrievalFocus` (q-runtime) is `{ ledger, boundRefs }`. It is set in `answer.ts` at the same point as `conversationState`: the shown ledger, plus the refs from a BOUND binding (about 20 lines in total). `packages/q-knowledge/src/q/evidence-retrieval.ts` plans its searches from it.
  - Note: the brief named `packages/model-gateway/src/q/evidence-retrieval.ts`. That file doesn't exist; the evidence context lives in q-knowledge.
  - The company specialist's `createRetrievalEvidencePort` (q-specialists) still runs one query. It gets the v2 reranker but no focus.

## Context Firewall

Authorisation still resolves before retrieval:

- **Filters only narrow.** A sub-query's subject filter goes through `narrowEnvelopeToSubjects`, which only ever narrows the envelope:
  - a subject-scoped constraint keeps only the overlap, or is dropped;
  - a constraint not scoped to subjects is narrowed to the subjects;
  - tenant, visibility and sensitivity are unchanged.

  A sub-query whose subjects the envelope can't reach is not run at all.

- **Hydration** still re-applies the full envelope.
- **The reranker can only reorder.** It sees only hydrated candidates. Ids it returns that aren't candidates are ignored. A candidate it leaves out keeps its fused place.
- **Diagnostics.** An empty envelope's result now has the same diagnostic keys (`queries`, `reranker`, `rerankMs`) as a searched one, so "denied" and "no match" still have identical shapes. The existing integration test caught this.

Negative tests:

- **Unit** (`q-knowledge/test/retrieval-context.test.ts`): a rewritten query can't reach another tenant's chunk or a founder-private chunk, even when each is the best match. Every search runs in the envelope's tenant with the founder-private way in dropped. An out-of-envelope sub-query never reaches the port. A hostile reranker can't add ids.
- **Postgres** (`retrieval.integration.test.ts`): the same property over real SQL. The ledger wrongly holds another tenant's company, and the reader binds it. Only the authorised network-visible chunk is returned, and neither marker appears.

## The bar: Q-IQ evidence questions with the needed fact in the final 8

The measurement code is `packages/q-evals/src/retrieval/q-iq-retrieval.ts`. Two tests run it: `test/q-iq-retrieval.test.ts` (in-memory) and `test/q-iq-retrieval.integration.test.ts` (**real Postgres FTS**: the production lexical and hydration SQL).

**How the needed facts are chosen.** They come from the dataset's own expectations, by code. For an ANSWER turn:

- Each fact carrying a required figure is needed; a contradiction needs both sides.
- Failing that, any fact carrying a required term other than an entity name.
- Failing that, any fact of each expected entity (overview turns).

Turns with none of these (UNKNOWN, CLARIFY, talk) aren't counted. That leaves **469 evidence turns**.

**Corpus.** Each Q-IQ fact is one chunk, headed the way a slide or data-room page heads it ("Monthly burn", "Customers (customer count)"). Each company also has six figure-free deck chunks that use the same vocabulary. There is no embedding runtime, which is lexical only, as in production today.

**Ledger per turn.** It is built from the case's earlier turns: entities in Q's replies or in the person's words, with ids. A name the person says for the first time is registered as words only (`id: null`).

**READER mode** binds the turn's expected entities that the ledger holds (or the company they belong to). It assumes the step-3 reader does its job, which only a live Q-IQ measures.

**The 22 misses:**

- **9 × "Who runs the first one?"** This is a vocabulary gap: "runs" vs "CEO". Lexical search can't bridge it; the semantic half would.
- **7 × "remind me of the first figure".** The figure is in Q's earlier reply, not in any question.
- **5 × "which company did I say I liked the team at?"** This needs cross-conversation recall (plan step 9).
- **1 compound.**

**Caveats:**

- The margin over 95% is two turns.
- The headings are a modelling choice. Without them, "customer count" can never reach "38 lending partners" lexically.
- The READER mode's binding is assumed, not measured.
