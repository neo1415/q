## What changed

### 1. Deep tool loop (`packages/model-gateway/src/q/tool-loop-budget.ts`)

- **Who gets it.** A turn is deep only when both of these hold:
  - the reader read it, or one of its parts, as `ANALYSIS`, `COMPARISON` or `DOCUMENT` (`readAnswerKinds`, step 4);
  - the existing `answerTaskClass` budgets it as `EVIDENCE_SYNTHESIS` or `COMPARISON`.
- **What it gets:** **5 rounds and 16 calls**, within a **30 s wall-clock budget**.
  - Once the budget is spent, no round beyond the standard two starts, and Q answers from what it holds.
  - A round that is already running is never cut short.
- **Every other turn** keeps 2 rounds and 10 calls. The constants `Q_TOOL_LOOP_MAX_ROUNDS` and `Q_TOOL_LOOP_MAX_CALLS` are unchanged.
- **Scope does not grow.** Every round gets the same offered tools, the same authorisation and the same Context Firewall. A test asserts that each deep round declares exactly the standard tool list. The other existing limits all still apply:
  - no chained round after public-web content;
  - the research hop;
  - `MODEL_TOOL_CALLS_MAX` per round.
- **Unknown classes fall back to two rounds.** If Step 7 renames task classes, the deep check stops matching and those turns get the standard loop.

### 2. Promise check (`packages/model-gateway/src/q/promise-check.ts`)

- **Input:** Q's own drafted output only, never the person's words.
- **Where it runs:** in `takeSentence`, right after the step 6 claim check, so voice never speaks an unbacked claim. The stored answer goes through `checkPromises` right after `checkAnswer`.
- **The ledger.** `createRunActions` records each run's acting results at the gateway's single tool port (`tools.execute`), where both code's calls and the model's calls pass. It is bounded at 200 runs.
- **What backs a claim** is structured data only:
  - the outcome status is `SUCCEEDED` and `result.ok` is true;
  - the classification is `SIDE_EFFECT` or `PREPARE` (a read or an analytical tool never backs an action);
  - the payload's own `status`, `outcome` or `action` code.

  | Result                                                                            | Backs                     |
  | --------------------------------------------------------------------------------- | ------------------------- |
  | `PREPARED`, `STARTED`, `QUEUED`, `SUGGESTED`, `RECOMMENDED`, `READY`              | PREPARE only              |
  | `SAVED`, `REMEMBERED`, `DOCUMENT_UPDATED`, `UPDATED`, `ADD`, …, or no code        | PREPARE and SAVE          |
  | `approve_pending_proposal` with `SAVED` or `SAVING`                               | every kind, SEND included |
  | `ONE_PER_TURN`, `NOT_CONNECTED`, `UNCHANGED`, `REFUSED`, …; an empty `added` list | nothing                   |
  | `request.writingDocument` (code files the answer as a document)                   | PREPARE                   |
  | A remember ask that code confirms (`rememberAsk`)                                 | SAVE                      |

  **Approval binding is unchanged.** A proposal waiting for approval backs "I've drafted" but never "I've sent" or "I've booked". No Q tool sends or books within a run.

- **The vocabulary** is documented in the file header, and a test keeps it at 30 verbs or fewer:
  - **PREPARE:** prepared, drafted, written/wrote, created, put together, built, generated, made. A PREPARE claim needs an artefact noun (document, brief, one-pager, deck, draft, email, message, update, …) or an object pronoun after the verb.
  - **SEND:** sent, emailed, messaged, forwarded, submitted, delivered.
  - **SCHEDULE:** scheduled, booked, and "set (up)" followed by a reminder, meeting or call.
  - **SAVE:** saved, added, noted, recorded, updated, pinned, stored, removed. A SAVE claim needs "your board / profile / mandate …" or an object pronoun after the verb.
- **Claim forms:**
  - "I've / I have (just / already / gone ahead and) X";
  - the simple past for unambiguous verbs ("I sent");
  - "it / that / this has been X" and "it's now X".
- **Not claims:**
  - negations and offers ("I haven't sent it", "I can draft it");
  - quoted text (a draft's own words), blockquote lines and code;
  - a sentence about an earlier turn ("yesterday", "last week", "earlier", "ago");
  - PREPARE claims that point at the answer itself ("drafted it below:", "here's the email I've drafted");
  - claims of answer content ("put together a summary").

  A question in the sentence does **not** shield a claim (F-106).

- **The rewrite.** Each kind gets one honest line per answer; later unbacked sentences of the same kind are removed.

  | Kind     | Honest line                                                                                                        |
  | -------- | ------------------------------------------------------------------------------------------------------------------ |
  | PREPARE  | "I haven't prepared that yet. I can prepare it for your approval."                                                 |
  | SEND     | "I haven't sent it; it's ready for your approval." when a proposal waits; otherwise "I haven't sent it."           |
  | SCHEDULE | "I haven't scheduled it; it's ready for your approval." when a proposal waits; otherwise "I haven't scheduled it." |
  | SAVE     | "I haven't saved that yet."                                                                                        |

- **Logging:** the warning `unbacked action claims rewritten in a Q answer` carries `where`, a count, the claim kinds and `toolsActed`. Like the `ungrounded` log, it never includes the text.
- **Exports:** `actionClaims`, `checkPromises`, `ACTION_CLAIM_KINDS` and the deep-loop constants are re-exported from `@capital-q/model-gateway/q`.

## Limits and next steps

- The vocabulary covers English. Like the step 6 claim check, a reply in another script is not checked. It fails open, so no wrong rewrite is possible.
- **The SEND path is conservative.** Only an applied approval backs "sent". If a future tool sends or books directly, add its applied code to `APPLIED_CODES` and give it SEND or SCHEDULE explicitly in `runActionOf`.
- **The deep loop's live effect is unmeasured** (no live calls). The next live Q-IQ should compare analysis, comparison and document-category latency and score on the merged head.
