# Onboarding speed and answer drops (2026-10-20)

Owner reports: founder and investor onboarding with Q **drops answers** (things said are never saved or acknowledged) and **takes a long time to reply**. Targets:

- zero silent drops: every stated answer is saved, or shown plainly as not saved;
- Q's next words start within about 1.5 s of the person finishing;
- nothing already answered is asked again.

Branch: `claude/onboarding-speed-878301`, cut from `speed/q-oct20` (`1cb6c83f0`). PR into `speed/q-oct20`. Ownership: onboarding and GateQ interview capture. Shared answer-path code touched: listed under "Shared code".

## Method

1. Traced every onboarding turn from the real code, not the docs:
   - web `onboarding-conversation/q-onboarding-workspace.tsx`, `conversation.ts`, `onboarding-kit/controller.ts`, `runtime-port.ts`, `api-actions.ts`;
   - `apps/api/src/http/onboarding.ts` (`/say`, thread);
   - `apps/q-api/src/voice/interview-route.ts`, `interview-agent.ts` (the one interviewer, typed and voice), `onboarding-port.ts`, `voice/turn.ts` (`answerInterview`, the voice path), `live/` and `duplex/` (every realtime turn goes through `ask_q` into the same `answerInterview`);
   - `packages/onboarding` (thread repository and use cases), `packages/contracts`;
   - GateQ: `apps/api/src/http/gateq-apply.ts`, `packages/gateq-intake` (`conversation-service.ts`, `interviewer.ts`, `postgres-intake-repositories.ts`), web `gateq/form/interview-step.tsx`.
2. Checked each item in `ONBOARDING-2026-10-16.md`, `ONBOARDING-FORM-PARITY.md` and the GateQ notes in `STATE.md` against the code (rows G1, G2 below).
3. Mapped every row to a fix, fixed it, then re-read the changed paths twice more against the code.
4. Wrote regression tests that reproduce each drop first. They fail on the old code (see Tests).

Timings: **modelled**, not production. They come from the repo's own bench (`apps/q-api/test/interview-latency.bench.test.ts`), whose latencies are taken from production traces: onboarding API round trip 150 ms, direct database read 40 ms, independent reading 1.5 s, tool round 1.8 s, reply round 1.6 s. The analysis that prompted this work measured the database hop at about 10 ms, so the I/O figures here are on the high side. No live provider was called.

## Timings (modelled, local)

Same machine, same benches, `CQ_BENCH_SCALE=1` (real modelled milliseconds). "Before" is `1cb6c83f0`'s `interview-agent.ts` and `onboarding-port.ts`, restored temporarily from git; "after" is this branch. Each turn time runs from the turn arriving at q-api to Q's reply being ready.

| Scenario                                                                                                  | Before                                    | After                                    |
| --------------------------------------------------------------------------------------------------------- | ----------------------------------------- | ---------------------------------------- |
| Founder typed turns, 9-turn bench (`interview-latency.bench.test.ts`), p50                                | 3,098 ms                                  | 2,787 ms                                 |
| Same, max (a refused answer re-sent over three rounds)                                                    | 6,287 ms                                  | 4,267 ms                                 |
| Same, API calls per clean turn                                                                            | 5                                         | 5 (one more write, one fewer read)       |
| Investor typed turn with seven mandate categories on record (`onboarding-investor-latency.bench.test.ts`) | 5,544 ms, 27 API calls, 21 category reads | 2,566 ms, 13 API calls, 7 category reads |

What this means against the targets:

- **Investor turns roughly halve.** Category names were re-read on every state read, one step after another. This matches the "investor first turn about 12.6 s" in ACTIVE-TASKS.
- **Founder turns gain about 300 ms at p50 and 2 s at the tail** (modelled 150 ms API, 40 ms DB). With the real ~10 ms database hop the absolute I/O saving is smaller, but the shape is the same: the turn's first reads are now one wait, not three, and the session is read once before the first round, not twice.
- **The 1.5 s first-words target is not met for typed turns.** A clean typed turn is one model round (modelled 1.8 s) plus reads, about 2.6–2.9 s, and the typed screen shows nothing until the whole turn ends (L9). Voice speaks each sentence as it is written. The rest of the gap is the model round itself, plus streaming on the typed path.
- Model calls per turn are unchanged: 2 for a clean save (the reader beside one round), 3 when a refusal needs words.

### What changed

- **Stages, from real events.** The turn reports READING ("Reading what you said" / "Getting your setup ready"), SAVING ("Saving your answers"), LOOKING_UP ("Looking up <company>") and WRITING ("Writing a reply"). They travel as an SSE `stage` event from q-api to api to the web route to `say-stream.ts`, and the workspace shows them in the working indicator.

- **Exact answers take no model call.** A one-word answer or a bare figure for the step just asked is saved by code and replied to by code (708 ms instead of 1.7 s for the first words).
- **What was saved is said first.** When a turn needs Q's judgement, code says what saved the moment the save commits ("stage: Seed; country: Kenya.") while the model writes the rest. The refused case ("Our gross margin is decent", with the model offering a figure they never said) has its first words at 3.5 s. It needs one model round to read the turn and one to word a reply, and neither can be dropped without cutting the guard or the reply's quality. Its stages show from 0 ms.
